# 拾光生活 AI 通用对话改造设计

日期：2026-09-17  
状态：已确认并实施

## 1. 目标

把当前分散在记录表单中的“聊两句、继续聊、帮我整理、整理预览”改造成用户熟悉的完整 AI 对话体验，同时保留拾光低负担、不过度打扰的产品气质。

生活栏目保留两个清晰入口：

- **快速记录**：一句话或一张照片直接保存，全程不调用 AI。
- **和拾光聊聊**：进入独立全屏对话，AI 短问慢聊；素材足够时主动建议生成一条生活记录。

本次改造的是生活记录中的上下文助手，不建设跨全部账本和生活数据的全局智能体，也不允许 AI 自动保存正式记录。

## 2. 已确认的核心体验

采用视觉方案 **A + A1**：完整聊天页，以及覆盖在聊天页上的记录确认抽屉。

主流程：

1. 用户在生活页点击“和拾光聊聊”。
2. 打开独立聊天页，拾光用一句轻问题开始。
3. 用户通过统一输入框发送文字，可按条添加照片。
4. AI 每次只回应一至两句、最多追问一个问题，不分析、不教育、不连续盘问。
5. AI 判断已经形成一个值得留下的片段时，在消息流中显示“生成记录 / 再聊聊”建议卡。
6. 用户点击“生成记录”，AI 根据当前会话生成结构化草稿。
7. A1 确认抽屉展示标题、正文、心情和标签建议。用户可以修改、返回继续聊或确认保存。
8. 只有点击“保存这条记录”后，内容才进入生活时间流；原始对话独立保存在本机，并可从记录中回看。

聊天关闭、网络失败或用户拒绝生成记录时，对话草稿都不丢失。

## 3. 页面与状态

### 3.1 生活页

顶部入口调整为：

- `快速记录`
- `和拾光聊聊`
- `拾光周刊`
- `AI 与隐私`

快速记录继续采用紧凑底部抽屉，只包含原话、照片、日期和折叠的扩展信息，不再混入 AI 消息、回复框或整理预览。

### 3.2 AI 对话页

页面结构采用常见聊天布局：

- 顶栏：返回、标题“和拾光聊聊”、本地草稿状态。
- 消息区：用户气泡、拾光气泡、失败/重试状态、生成记录建议卡。
- 输入区：添加照片、文本输入、发送/停止按钮。

打开空会话时，首句为轻量邀请，例如“今天有什么小事，想让我陪你留一下？”。恢复草稿时直接回到原位置，不重复首句。

用户可随时退出。返回先关闭照片选择、授权确认或摘要抽屉，再退出聊天页。

### 3.3 生成记录建议卡

建议卡属于消息流的一部分，但不是普通 AI 文本。仅在 AI 返回明确的 `readyToSummarize` 状态时出现：

- 主操作：`生成记录`
- 次操作：`再聊聊`

“再聊聊”只隐藏当前建议卡，不丢弃对话。后续新增用户消息后，AI 可以再次建议。

若模型响应无法解析为结构化结果，则只显示普通回复，不猜测“素材已经足够”。

### 3.4 A1 确认抽屉

确认抽屉覆盖在聊天页上，不跳转到传统表单页面。默认展示：

- 可编辑标题。
- 可编辑生活记录正文。
- 心情建议。
- 标签建议。
- 折叠的照片、日期、回访和关联账单信息。

操作包括：

- `保存这条记录`：原子保存正式记录和本地会话引用。
- `返回继续聊`：关闭抽屉，保留当前摘要方案。
- `重新整理`：用户明确触发后，根据最新会话生成新方案。

会话继续产生新消息后，旧摘要标记为“对话已有新内容”，不会静默更新或覆盖用户在抽屉中的修改。

## 4. AI 行为与提示词边界

聊天接口返回结构化结果：

```ts
interface LifeChatTurnResult {
  reply: string;
  readyToSummarize: boolean;
}
```

摘要接口独立返回：

```ts
interface LifeSummaryProposal {
  title: string;
  body: string;
  mood?: string;
  tags: string[];
  sourceMessageCount: number;
}
```

聊天提示词约束：

- 回应保持简短、自然，一次只问一个问题。
- 优先追问可感知的小细节，不要求用户解释意义。
- 不诊断情绪，不提供医疗或心理结论，不说教。
- 用户明显想结束、拒绝回答或只想保存时停止追问。
- 没有形成具体片段时不得建议生成记录。

摘要提示词约束：

- 只使用当前会话中用户提供的事实。
- 不虚构地点、人物、感受或因果。
- 保留用户口吻，避免鸡汤化和过度文学化。
- 正文是一段可直接进入生活时间流的短记录，不包含 AI 问句。

## 5. 数据设计

现有快速记录继续使用 `LifeDraft.body`。AI 会话使用 `LifeDraft.messages`，两条路径不再在同一界面混用。

新增类型：

```ts
interface LifeSummaryProposal {
  title: string;
  body: string;
  mood?: string;
  tags: string[];
  sourceMessageCount: number;
}
```

`LifeDraft` 增加可选的 `summaryProposal`。正式 `LifeNote` 增加可选的本地 `conversation`，保存用户与 AI 的原始消息，供回看和解释摘要来源。会话不会自动加入周刊素材；周刊仍只读取用户确认后的正式生活记录。

摘要方案与正式字段分离：生成摘要不得直接修改 `title`、`body`、`mood` 或 `tags`；只有用户在确认抽屉中接受或编辑后才写入正式记录。

数据库不需要新增索引。备份格式扩展以包含会话和摘要草稿；恢复后仍强制关闭 AI 总开关。

## 6. 组件边界

- `lifeQuickComposer.ts`：纯快速记录和普通记录编辑。
- `lifeChat.ts`：全屏会话、输入、照片、消息状态和生成建议卡。
- `lifeSummarySheet.ts`：A1 摘要确认、编辑和保存。
- `lifeAiConsent.ts`：本次会话的目标与素材授权。
- `lifeAiRepo.ts`：聊天与摘要两个结构化请求，不负责 UI 状态。
- `lifeDraftRepo.ts`：草稿、摘要方案、正式记录与会话的原子保存。

拆分后，快速记录不依赖 AI 仓库；聊天页也不直接操作正式记录表。

## 7. 授权与隐私

- AI 总开关默认关闭。
- 新打开或恢复一次会话后，首次发送前展示服务地址、模型和将要发送的文字范围。
- 页面保持打开、目标未变化且只继续发送文字时，不重复弹窗。
- 新增或首次发送照片、模型或服务地址变化、关闭后重新打开会话时必须重新确认。
- 照片默认不发送；用户按消息明确选择后才进入请求。
- 目标在授权后、实际请求前再次校验，防止配置变化导致发送到未确认的服务。
- 关闭 AI 总开关立即取消在途请求，但保留本地消息和草稿。
- 日志、Toast 和错误信息不得包含服务方返回的私密正文。

会话授权只保存在当前页面内存，不写入数据库；重新打开必须重新确认。

## 8. 错误与恢复

- 发送失败：用户消息保留，在对应位置显示“发送失败 / 重试”。
- 生成被取消：保留已有会话，不产生空 AI 消息。
- 结构化聊天响应无效：降级为安全的普通文本回复；不显示生成建议。
- 摘要响应无效：保留对话和旧摘要方案，提示重新整理。
- 草稿写入失败：保留当前页面内存副本，允许关闭后重新打开重试。
- 正式保存冲突：不覆盖后来更新的生活记录，保留确认抽屉中的编辑内容。
- 照片变化：清除依赖旧照片的未确认摘要，并明确提示用户。

## 9. 兼容与迁移

- 已保存生活记录、周刊、账单故事和回访行为保持不变。
- 旧版同时包含 `body`、`messages` 和 `aiText` 的未完成草稿，首次打开时迁移到聊天会话：原话成为首条用户消息，旧 AI 整理稿作为待确认摘要。
- 旧生活照片继续原样保留；只有新添加图片执行 JPG/PNG/WebP 和体积限制。
- 不修改底部导航顺序、账务口径或账单关系。

## 10. 验收标准

自动化覆盖：

- 快速记录不触发任何 AI 请求。
- 首次授权、连续文字消息免重复授权、照片和目标变化重新授权。
- 多轮对话、停止、失败、重试和草稿恢复。
- AI 主动建议、继续聊天、生成摘要、摘要过期、重新整理。
- A1 修改后保存，正式正文与原始会话分离。
- 旧草稿迁移、备份恢复、周刊与账单故事回归。
- 360、390、430px 和桌面 PWA 的布局、触控尺寸、键盘与分层返回。

最终执行完整单元测试、生产构建、浏览器回归和敏感信息检查。Android 构建与真机验证是否执行，按当轮用户要求决定。

## 11. 非目标

- 不建设能查询全部账目和生活历史的全局 AI 助手。
- 不让 AI 自动创建、修改或删除正式记录。
- 不自动把原始会话加入周刊。
- 不在后台主动调用 AI。
- 不在本次改造中加入语音识别；仅为未来语音输入保留统一输入区位置。
